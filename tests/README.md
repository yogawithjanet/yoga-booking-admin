# 自動測試（給 Janet 測試用）

## 怎麼跑
需要 Node.js 20 以上。把 `yoga-booking` 和 `yoga-booking-admin` 兩個 repo 放在同一個資料夾裡（前台測試會讀 `../yoga-booking/index.html`）。

```bash
cd yoga-booking-admin/tests
npm install
npm test
```

約 2–3 分鐘，最後看到 `# fail 0` 就代表全部通過。

**不會碰到正式資料**：所有測試都在電腦記憶體裡的資料庫（PGlite）執行，每個測試建立一個全新的資料庫。不讀 `config.js`、不連線 Supabase、不需要任何金鑰。

## 檢查了什麼（共 171 項）

| 分組 | 檔案 | 檢查內容 |
|---|---|---|
| 1. 資料安全 | `migration-safety.test.js` | 跑第一、二階段 SQL 前後，所有資料一筆都沒變；重複執行也不會改資料；跑完第一階段舊網站照常能用；回滾能恢復舊權限；上線前檢查只讀不寫 |
| 2. 資安權限 | `db.test.js` | 只有公開金鑰的人讀不到、改不了任何學員資料；學員只看得到自己的資料；學員不能用管理員功能；新註冊帳號不能把自己變管理員 |
| 3. 預約 | `db.test.js` | 預約扣 1 堂；重複、額滿、已開始、未開放、停課日都會被擋且不扣堂；兩人搶最後一個位子只有一人成功；不會用到上課前就過期的堂數；買 17 約 17 剩 0 |
| 4. 取消 | `db.test.js` | 取消退 1 堂、連按只退一次；超過時限不能取消；不能取消別人的；沒扣過堂的預約取消不送堂 |
| 5. 堂數與過期 | `db.test.js` | 用台北時間判斷過期；後台扣的堂數不會被加回來；扣超過整筆失敗；加堂與收入一起成功或一起失敗；設定 / 編輯 / 刪除批次數字正確 |
| 6. 課程異動 | `db.test.js` | 停開某天會退堂；固定課改特別課預約會搬過去；刪課程未來退堂、過去標記完成；上完的課自動標記完成；時間格式錯誤的舊資料不會讓功能出錯 |
| 7. 金流與其他 | `db.test.js` | 多人收支一次新增、金額 0 或負數被擋；每筆異動記錄是誰改的；刪除學員時金流保留 |
| 8. 前台實際操作 | `frontend.test.js` | 預約、取消、時限、過期、課表、註冊資料；畫面資料過舊時伺服器仍會擋；惡意文字不會被執行；LINE 驗證失敗讀不到資料；載入失敗顯示錯誤 |
| 9. 後台實際操作 | `admin.test.js` | 加減堂、設定堂數、幫學員預約 / 取消、超收確認、停課、轉特別課、刪課程、人數驗證、刪批次、收支、名單、熱門度、惡意文字、非管理員無法登入 |
| 10. 副作用檢查 | `regression.test.js` | **新舊版畫面比對**：修改前的舊版與新版，前台 9 個畫面、後台 13 個頁面逐一比對，內容必須完全相同；**舊功能實際操作**：沒改到的 31 項後台功能（店名、主題、公告、關於我們、標籤、老師、課程範本、開放區間、取消時限、註冊題目、清除註冊資料、收支編輯刪除、名單、教學紀錄）實際執行並確認資料寫入。兩者都在第一、二階段兩種權限下跑，並檢查沒有任何資料庫錯誤 |

名稱含「修正 Cx / Sx / Fx」的測試對應 PR 說明裡的問題編號，在修正前的程式碼上是紅燈。

## 看到失敗怎麼辦
失敗的測試會印出測試名稱與「預期 / 實際」的差異。副作用檢查失敗時，會列出「只在舊版」「只在新版」出現的畫面文字。把整段輸出貼給開發者即可。

## 測試架構（開發者參考）
| 檔案 | 用途 |
|---|---|
| `sql/00_supabase_stub.sql` | 模擬 Supabase 平台（角色、`auth.jwt()`、storage、**新物件預設開放給 anon 的授權**） |
| `sql/01_baseline_schema.sql` | 修改前正式環境的結構與寬鬆權限 |
| `pg.js` | 建資料庫、種子資料、套 `supabase/migrations/`、以角色執行、可控時鐘 |
| `supabase-shim.js` | supabase-js → SQL 的轉接層（迷你 PostgREST，RLS 真的生效，並記錄所有資料庫錯誤） |
| `load-app.js` | 把前台 / 後台 `index.html`（或任一版本）的程式碼載進 Node 執行 |
| `fixtures.js` | 共用測試資料（時間基準 2026-09-28 10:00 台北） |
